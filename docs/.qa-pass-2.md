## BLOCKERS

### B1. "Reads never prompt" is false — the kernel gates `actions.read` too, and Recipes' own read actions are the reason it does

**Location:** `docs/internals.md:491-493` (`recipes-cross-app-actions`).

**What the doc says:**

> Reads never prompt (side-effect-free); writes hit the kernel's one-time grant
> dialog — *Allow once / Always / Block*, **per calling app, per action**.

**Evidence** — `ConjureOS/src/kernel/actionRegistry.ts:422-440`:

```
    // Permission gate — fires for BOTH read and write actions when invoked
    // by a sandboxed app (not when the orchestrator invokes directly; the
    // orchestrator is trusted shell code).
    //
    // Phase 30b (#220): extended to also gate `actions.read`. Without this,
    // any installed app could silently enumerate another app's read actions
    // (e.g. a "calorie tracker" reading the full recipe library) the moment
    // it's installed. The dialog distinguishes the action kind so users can
    // make informed decisions ("Allow X to see your recipes?" vs
    // "Allow X to add a recipe?").
    if (
      (meta.permission === "actions.write" || meta.permission === "actions.read") &&
      callerAppPath !== null
    ) {
      const grant = await this.resolveGrant(callerAppPath, staticEntry, actionName, meta);
```

The kernel comment's worked example — *a "calorie tracker" reading the full
recipe library* — is **this app's** `listRecipes` being read by **this doc's**
running example (Conjure Health). The gate was added *because* read-only
enumeration of Recipes was the threat.

The second half of the sentence is correct: `resolveGrant`
(`actionRegistry.ts:483-512`) offers `once` / `always` / `block`, persists
`always` and `block` into the **caller's** manifest keyed by target app path
then action name — i.e. per calling app, per action.

**Why blocker:**

1. It is a **security-model** claim, stated as a property of the platform, in
   the section the doc itself opens with *"Recipes is the worked example in the
   external developer docs, so the exact shape matters"* (`:436-437`). Told
   "reads never prompt", a third-party developer designs a provider assuming
   read actions are silently invocable and a consumer assuming reads need no
   consent UX. Both are wrong, and the failure is a surprise permission dialog
   in someone else's app.
2. It contradicts the doc's own posture elsewhere — `recipes-identity-and-roles`
   is careful that nothing is trusted client-side; this sentence hands away a
   consent boundary.
3. It is exactly the class of error pass 1 flagged as B5/S6: an assertion about
   *shape* made without reading the enforcing code.

**Should say:** every cross-app invoke from a sandboxed caller prompts — reads
included, since Phase 30b (#220) — with the dialog wording differentiated by
action kind ("see your recipes" vs "add a recipe"). The grant is *Allow once /
Always / Block*, recorded per calling app, per target action, in the caller's
manifest; only the shell's own orchestrator bypasses the gate.

### S1. The load-bearing layer rule lists two exceptions; there is a third, and the first one is mischaracterized

**Location:** `docs/internals.md:108-114`.

**What the doc says:**

> `window.__conjureos` or `window.__vfs`. … Two deliberate exceptions, both

**Evidence** — every host-global reference outside `src/bridge/`:

```
$ grep -rn "__conjureos" src/ --include=*.ts --include=*.tsx | grep -v "^src/bridge/"

Two errors:

1. **`src/features/familyLink.ts` is an unlisted third exception**, and it is
   live, not dead: `src/screens/FamilyScreen.tsx:11` imports
   `familyInviteLink` / `parseInvite`.
2. **The nutrition exception is not "HTTP rather than host access."**
   `nutrition.ts:54-55` reads `globalThis.__conjureos.env.usdaProxyUrl` — that
   *is* host access, from the features layer. The doc's justification for the
   exception describes something the code does not do.

Compounding, `familyLink.ts:29-30` decides the environment by **string-matching

  const a = api();
  if (a.includes("ntgelbtepecqsqloxmct")) return PROD_WEB; // prod project

contradicts `recipes-de-vite-migration` at `:1005-1008`: *"Anything

**Should say:** three modules outside `src/bridge/` touch the host global —
`nutrition.ts` and `familyLink.ts` both read `__conjureos.env.*` — and drop the

`familyLink.ts`'s hardcoded project-ref → web-origin mapping as a live

### S2. "`conj-pack`'s validator warns" is presented as an emitted warning, but nothing in this repo's flow ever emits it — and the pinned pack has no such check

**Location:** `docs/internals.md:479-487` (`recipes-cross-app-actions`, the schema-gap subsection).

**What the doc says:**

> The consequence is concrete, not cosmetic. `conj-pack`'s validator warns:
> > `conjureos.actions.importRecipeFromImage` has no `returns` schema …
>
> (`conjureos-pack/src/validate.ts:508` …)

**Evidence:**

- The message exists — but at `validate.ts:508` of **pack `0.2.0`**
  (`/home/user/conjureos-pack`, `package.json` version `0.2.0`, 691-line
  `validate.ts`), verbatim as quoted, with the strict/`needs` ERROR branch at
  `:496`. That part is right.
- The pack **this repo installs** is `0.1.1`
  (`node_modules/@conjureos/pack/package.json`), whose `validate.ts` is **317
  lines** and contains no `params`/`returns` check at all
  (`grep -n "returns" node_modules/@conjureos/pack/src/validate.ts` → one hit,

  `grep -n "validate" ConjureOS/scripts/publish-app.mjs ConjureOS/scripts/bundle-app.ts` →

### S3. `recipes-local-storage` presents itself as the complete device-state inventory and omits `localStorage`

**Location:** `docs/internals.md:530-548` — *"What remains on the device … "* followed by an exhaustive-looking table.

**Evidence** — three `localStorage` keys, in two modules:

```
src/features/storeLayout.ts:118  return localStorage.getItem(AI_SORT_KEY) !== "off";
src/features/storeLayout.ts:125  localStorage.setItem(AI_SORT_KEY, on ? "on" : "off");

The section's headline claim ("nothing recipe-shaped is written to the device")

This matters more than usual for a sandboxed app: `localStorage` is scoped to

partitioning, backup, and clear-data behavior from the VFS — and unlike the VFS
it is invisible in the Files app, which the section uses as its framing
("browseable in the Files app").

**Should say:** add a short second table or paragraph — the AI-aisle-sort
toggle and last-selected store (`storeLayout.ts:118-145`) and the Plans
last-view (`PlansScreen.tsx:41-50`) live in per-app-origin `localStorage`, not
the VFS, and are not visible in the Files app.

### S4. The realtime/identity section never says how a sandboxed app obtains the anon key — its own backend hands it over

**Location:** `docs/internals.md:185` (bridges table) and `:594-599` (`recipes-identity-and-roles`, "**Realtime**").

**What the doc says:** *"the app has only the public anon key, so
`postgres_changes` is impossible"* and *"a dependency-free Phoenix-channels
client … over the public anon key."* Both treat the key as simply present.

**Evidence** — it is delivered by the backend, over the minted-token channel:

- `ConjureOS/supabase/functions/recipes-db/index.ts:568` — `myProfile` returns
  `anonKey: Deno.env.get("SUPABASE_ANON_KEY") ?? ""`.
- `src/screens/PlansScreen.tsx:111` — `const anonKey = profile?.anonKey ?? "";`
  then `:130-132` passes it into `subscribeFamilyChannels`.
- `src/bridge/recipesApi.ts:502,508` — the dev mock profile ships
  `anonKey: ""`, and `PlansScreen.tsx:120` short-circuits on an empty key.

Two things follow that the doc should carry, given how carefully it treats the
"the app never holds a Supabase session" boundary:

1. The app *is* handed a credential by its own backend, gated behind the minted
   token — the design is deliberate (anon key is public, but the delivery path
   is worth stating in a section whose whole subject is what the app may hold).
2. **Realtime is silently inert under `npm run dev`** (empty `anonKey` → the
   subscribe effect returns early). The doc claims elsewhere (`:118-120`) that
   every bridge ships a mock "so the whole UI boots" — true, but family
   live-update is one flow that cannot be exercised locally, which is worth
   knowing before someone debugs it.

**Should say:** the anon key reaches the app as a field on `myProfile`'s
response (`recipes-db/index.ts:568`), i.e. only after minted-token verification;
the dev mock returns an empty key, so realtime is a no-op under `conj-pack dev`.

### S5. The nutrition section repeats a source comment that the shell contradicts, and misses a live TODO

**Location:** `docs/internals.md:625-630` (`recipes-nutrition`) and `:1257-1261` (related decisions).

**What the doc says:** the proxy URL is resolved at runtime from
`globalThis.__conjureos.env.usdaProxyUrl` "with a fallback to the dev proxy",

**Evidence, both directions:**

  `ConjureOS/src/kernel/sandbox.ts:130-133` derives

- But the app's own comment says the opposite and is not in the doc's
  stale-comment list — `src/features/nutrition.ts:43-50`:

  > 1. … (`window.__conjureos.env.usdaProxyUrl`), use it … (**additive/future;
  > absent today.**)
  > …
  > **TODO(backend): deploy `usda-proxy` to prod and expose `env.usdaProxyUrl`
  > on the host bridge so prod installs hit the prod proxy automatically.**

  The first half ("absent today") is stale — `sandbox.ts:1040` injects it. The
  second half is an **unresolved deployment question the doc does not raise at

Given the doc's discipline elsewhere about flagging what it cannot verify from
this repo (`recipes-open-questions`), this belongs there.

**Should say:** the URL is injected per-environment by `sandbox.ts:130`; the

Add `nutrition.ts:43-50` to the stale-comment list ("absent today" is no longer
